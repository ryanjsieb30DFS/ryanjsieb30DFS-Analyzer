# CLAUDE.md — DFS Slate Analyzer

Article-driven, multi-sport DFS slate-strategy tool for DraftKings. Streamlit web app. Personal-use, single user (`ryanjsieb30`).

## What this is

A pre-slate / post-slate **slate-strategy** tool for **PGA Classic, PGA RD4 Showdown, MMA, NASCAR**. The user uploads the slate's **articles** (PDFs, notes, data files, screenshots) AND vendor **projections**, and Claude synthesizes a written **slate strategy**: top plays, how to approach the slate, key themes, leverage & fades, and the decisions that define the slate. After the contest, the user uploads DK contest-standings and the Analyzer drives a post-mortem + learning loop.

**No lineup building. No ranking, red-teaming, or fixing lineups.** Lineup construction lives solely in the separate sim tool. This tool is a strategy doc the user hand-builds from — the **slate strategy is derived from everything uploaded (articles + every loaded vendor projection)**, cross-checked against the strategy docs. The **autopsy stays standings-only** (it never REQUIRES projections; since 8/11/26 salary/proj fields fill best-effort from still-loaded projections and stay None when cleared/unmatched). **Selection is not construction (8/9/26):** the Analyzer still NEVER authors, edits, swaps, or fixes a roster — but PICKING among the Sim's ALREADY-BUILT, already-simmed pool lineups is permitted, in the Grade tab's per-contest flow ONLY (`src/lineup_selection.py` + `run_contest_selection`): per contest, claude reads that contest's candidate slice (~100 real pool rows with THAT contest's sim numbers — expanded from 50 by user directive 8/15/26) + the strategy + open lessons and picks exactly `my_entries` rows BY ID; `parse_pick` rejects fabricated ids, modified rosters, wrong counts, any lineup already picked for another contest, and any lineup that breaks the strategy gate — a bad pick saves NOTHING. **THE PICK MUST FOLLOW THE SLATE STRATEGY (user directive 8/15/26).** The strategy is a GATE, not advice: `strategy_gate` + `eligible_indexes` remove every non-compliant lineup from the pool BEFORE the slice is cut, so sim numbers only ever decide BETWEEN lineups the strategy already allows. No strategy contract → no pick at all (the button is disabled). **One lineup, one contest (user directive 8/15/26, ALL sports):** across a slate's contests a pool lineup may be picked ONCE — already-picked rosters are cut from every other contest's slice and re-rejected by roster identity if one slips through. **TWO OPINIONS PER CONTEST (user directive 8/22/26):** the Sim also pushes its DIVERSIFIED portfolio (`data/sim_entries/<slug>.json`), and each contest's Grade section shows that set beside claude's own pick — both A-F graded on the same contest calibration, with `lineup_selection.compare_sets` counting how many lineups the two chose in common. The pick stays deliberately **BLIND** to the Sim's set (never in the slice, the prompt, or the validation): agreement is evidence only if the two chose independently, and an informed pick agreeing with what it was shown is just anchoring. **Overlap is a fine outcome, never an error.** The Sim's entries are never gated away — one that breaks the slate strategy is FLAGGED with the rule it breaks and stays gradeable and loadable, because that override is the user's. Buttons load either set (or both, deduped) into the contest's working box; the box is what actually gets graded. The user reads both and decides what to enter in DK; nothing flows back to the Sim. The slate-strategy, player-pool, and (thesis) grade runners keep their full bans: they still never select.

There is a **Projections** tab for uploading vendor projection CSVs (auto-detected, stored per slate). Besides storing/viewing them it computes a **Breakdown** that surfaces non-obvious edges (chalk tiers + concentration, leverage board, ownership-vs-ceiling mispricing, value-by-tier, AM/PM tee-wave split, boom/bust, auto-flagged "edges to notice", and cross-vendor disagreement when ≥2 sources are loaded). The loaded projections are **also folded into the bundle** so the slate strategy reads them alongside the articles. The autopsy still does NOT read projections.

Five tabs: **Projections → Slate Data → Slate Strategy → ✅ Grade → Autopsy**. The **Grade** tab is PER-CONTEST (8/9/26 — user directive: "not every contest is the same"): one bordered section per contest (Sim-pool contests merged with declared ones via `match_contests`; declared-only contests get a grade box without the pick button). Per contest: (a) **🎯 Have Claude pick** — `run_contest_selection` reads that contest's candidate slice (~100 real Sim pool rows with THAT contest's own sim numbers), the strategy, and open lessons, then picks exactly `my_entries` rows BY ID; `lineup_selection.parse_pick` validates hard (fabricated id / modified roster / wrong count / **a lineup already picked for another contest** / **a lineup that breaks the slate strategy** → rejected, nothing saved); the slice itself is pre-filtered by the **strategy gate** so only strategy-compliant lineups are ever on the table, and with no strategy generated the pick button is disabled; the pick renders with its why and one-click loads into the grade box. (b) **A grade box with an A-F LETTER** — deterministic `grader.letter_grade` calibrated to THIS contest (`contest_calibration`: its field size, payout shape, size-gated history): hard F on a fade violation or over-cap salary or 4+ warnings; else warns 0→A/1→B/2→C/3→D; one-step sim adjustment when the pasted roster IS a pool row (metric follows payout shape: top-heavy→top1 percentile, flat→cash percentile; ≥90th up, <25th down); section headline = WORST lineup letter; every letter ships plain-language why lines. (c) an optional per-contest `claude -p` thesis check (`run_grade(contest=…, file_key=…)` → `data/grade/<slug>__<key>.md`). A bottom expander holds the cross-contest portfolio view (leverage table + a duplicate check — DK would allow reuse, but **one lineup, one contest** is the rule since 8/15/26, so a lineup showing up in two contests is a ⚠️ warning, not info). **It grades and names weaknesses only — it NEVER builds, swaps, or fixes lineups.** (The former **Sim Data**, **Post-Contest Sim Data**, and **Trends** tabs were removed — the first two with the SaberSim retirement, Trends as part of the strip-down; their modules are dormant on disk, see below.) The Slate Strategy tab also has a **Player pool** below the written strategy — a Claude-generated, ranked, annotated board of every rosterable player, each tiered **Core / Good / Okay / Fade** (+ an orthogonal `· Leverage` label) with a short GPP write-up. This board is the primary build reference. Built automatically as part of the slate-strategy generation (no separate button).

## Writing the slate strategy

This normally runs **in-app**: the Slate Strategy tab's **Generate slate strategy** button calls `src/analysis_runner.py::run_analysis`, which builds the bundle and invokes `claude -p` headlessly (subscription auth, no API key) to read the bundle + referenced files and write `data/slate_analysis/<slug>.md`. That headless Claude loads this `CLAUDE.md` and follows the steps below. The same can be triggered manually from chat (fallback): click the button once to build the bundle, then ask **"read the bundle and write the slate strategy"**. Either way:

1. Read the bundle: `data/bundle/<slug>.md` — it lists the declared contests, absolute paths to every `articles/<slug>/` file, the `## Projections` tables (every loaded vendor), and the strategy-doc paths. Start here.
2. Read every slate-data file it lists under `articles/<slug>/` — `*.pdf`, `*.txt`/`*.md`, `*.csv` (misc data like vegas odds or course/track history — read as text tables), and `*.png`/`*.jpg`/`*.jpeg` (use the Read tool — it reads images visually, so DailyFan screenshots work; PDFs may require poppler — note in the file if anything couldn't be parsed). Then read the `## Projections` tables in the bundle — every loaded vendor's ownership/projections.
3. Read strategy: `rules/<slug>/{philosophy,framework,autopsies}.md` + `rules/shared/anchor_equivalence.md` + `rules/shared/sharp_playbook.md` (paths are in the bundle).
4. Read recent autopsies: tail of `rules/<slug>/autopsy_data.jsonl`.
5. For NASCAR: also read `rules/nascar/tracks/<track>.md`.
6. Synthesize from the ARTICLES **and the projections together**, cross-checked against the framework + open lessons:
   - What do the articles + projections surface as the top plays, and where do they DISAGREE — article vs article, vendor vs vendor, or article vs projection (that disagreement is the edge)?
   - Which qualitative reads should drive the build, and where do the projection numbers confirm or challenge them? What's the Anchor-Equivalence call?
   - Which framework rules / open lessons activate?
7. Write to `data/slate_analysis/<slug>.md` in the format below. It renders in the Slate Strategy tab with a "Last updated" timestamp and is cleared automatically when the user logs an autopsy.

**Coverage rule:** read EVERY uploaded slate-data file — every article PDF, note, data CSV, AND photo/screenshot — never silently skip one. The slate strategy reads them all **silently** (no printed checklist — the user doesn't want one); the Player pool still ends with a `## Sources read` line stating how many files were read and listing any it couldn't parse.

**Source-of-truth rule:** synthesize from EVERYTHING uploaded — the articles AND every loaded vendor projection — cross-checked against the framework and open lessons. Blend the qualitative article reads with the projection ownership/projections; cite each number from its source (name the **article OR the vendor**). Where vendors disagree with each other, or a vendor disagrees with the articles, surface that gap — it is leverage signal. Write **no lineup tables** and build **no rosters**; this is a strategy doc the user hand-builds from.

**Leverage-coverage rule:** when projections are loaded, the bundle includes a `## Leverage candidates to address` section — the sub-10%-owned, high-ceiling plays (`src/landscape.py::leverage_candidates`). **Every** listed player MUST be ADDRESSED in the slate strategy's `## Leverage` or `## Edges & tensions` with a one-line synthesis of their leverage/ceiling case (surface it — no play/fade command required), and the Player pool must confirm each in its `## Leverage candidates addressed` footer (ranked, `· Leverage`-labeled — or tiered `Fade` with a reason). A sub-10% high-ceiling play left unmentioned is a coverage leak — the play that decides the slate from nowhere (the Kaan Ofli failure, 6/27 Baku). The app shows a **coverage-gap warning** if the rendered strategy omits any candidate.

**Chalk-combo duplication rule:** when projections are loaded, the bundle includes a `## Chalk combos` section (`src/landscape.py::chalky_combos` — this slate's highest-owned pairs with expected co-occurrence × field size). The strategy MUST surface the top combos in `## Edges & tensions` as a duplication tension in plain English ("the field will pair X + Y in ~6.6% of lineups, ~235 in this field") — descriptive only; breaking a pair is the user's call. This is the forward-looking complement to field_tendencies' historical recurring pairs.

**Field-tendency coverage rule (SHAPE-first 7/31/26; conditions-only traps 8/9/26):** when the bundle includes a `## Field tendencies` section (≥2 comparable logged autopsies — `src/field_tendencies.py::bundle_block`, history gated to 0.5×-2× of the declared contest's field size), the strategy MUST surface its content in `## Edges & tensions`. **A TRAP IS A PRICE, NOT A DRIVER (user directive 8/9/26):** no player is ever a trap; a trap is a salary + projection + ownership shape, and those numbers reset every slate. Trap history therefore renders ONLY as the trap SHAPE (the price conditions the losing half keeps buying: chalk share, owned-ahead-of-projection share, salary tier — k-of-t counts), never as a player name, and a cross-slate name count is NEVER fade/underweight evidence — every fade cites THIS slate's numbers (a same-projection peer at lower own, ownership outrunning projection rank; the bundle's `## Trap-shaped prices` section computes exactly this from the current projections, where naming players IS fine because they're today's prices). CROWD names are different and are kept: they map where the user's OPPONENTS reliably go (the same small fields re-enter these contests) — surfaced with in-N-of-M counts as opponent behavior/leverage-away only, never player quality; the Player pool tags them `(field crowds)`. The block leads with the OWNERSHIP SHAPE; names appear only when the player is on the CURRENT slate (on-slate filter via loaded projections; MMA usually degrades to pure shape). The app's **field-tendency coverage-gap warning** fires ONLY for on-slate crowd names. All descriptive; no fade commands.

### Slate strategy format (mandatory, all sports)

**SYNTHESIS-FIRST, tight, scannable.** **This tool ORGANIZES and SYNTHESIZES the data — it does NOT tell the user who to play.** Surface edges, tensions, mispricings, and rankings; the user makes every play/fade/build decision and builds in the Sim tool (the sibling repo). No imperative play/fade commands, no roster shaping. **NO pre-flight/checklist section is printed** — that prep (venue file, open lessons, framework pre-lock checks) happens silently and only its RESULT shows below. **Hard writing rules, all sections — WRITE FOR A SMART 5TH GRADER (user directive 7/27/26: "spell it out like it's for a 5th grader"), AND KEEP IT SHORT (user directive 8/9/26: the old "more words is totally fine" is revoked — a 6,000-word brief takes 25 minutes to read; the doc must be compact, simple, straightforward). This applies to EVERY generated output: slate strategy, player pool, grade, AND the post-autopsy review.**

**LENGTH: the slate strategy budget is 5,000 words (raised by the user 8/29/26 from 2,200); aim 3,000–4,500. The post-autopsy review stays at 1,800.** The extra room is for CLARITY, never for length — spend it explaining what a number MEANS, walking the reasoning a step at a time, and saying what the field will do and how the slate beats it. **More room is not permission to get complicated:** the 5th-grader rule governs every sentence at 5,000 words exactly as it did at 2,200, and a longer document that is harder to read is a WORSE document. Use the space for more short sentences, not longer ones.

**"EVERY generated output" MEANS EVERY STRING THE USER READS (user directive 8/29/26: "literally anything that is being output").** Not just the Claude-written documents — app captions, `gate_summary`, `contract_conflicts`, warning banners, table help text, and every diagnostic message are held to the same bar. Concretely: no bare statistics vocabulary (say "how many teams will pick him", not "ownership priced against win probability"; say "about 1 in 30", not "sims at 3.3%"), no internal identifiers, and every number gets its plain meaning in the same sentence. If a string names a column, say what the column means. The pick rationale has its own extra contract — see the `## The pick rationale` note below.
1. **The 5th-grader test is the master rule.** Short sentences. Ordinary words. One fact at a time. If a smart 11-year-old would re-read a sentence or ask what a word means, rewrite it. Clarity wins every tie — but say it ONCE, in the fewest plain words that stay clear.
2. **Plain meaning FIRST, DFS word in parentheses after — EVERY time, every section.** 'The players most teams will pick (the chalk)', never 'the chalk (the most-picked players)'. Do not assume a term stuck from an earlier section — the user has said the verbiage loses him. Applies to: ownership, chalk, leverage, ceiling, floor, dupe/duplication, anchor, anchor-equivalence, fade, dominator, place differential, fish trap, own-per-slot, stars-and-scrubs, punt, and all vendor terms (coffin, dock, boost, sim-optimal, steam).
3. **Every section opens with one plain sentence saying what the section is for** ('This section shows where most of the crowd is putting their players.').
4. **One idea per sentence, ~15 words, hard stop at 25.** No semicolon/dash chains; max two numbers per sentence. Density AND length are both enemies — one idea per sentence, and no idea said twice (the 7/26 NASCAR brief ran 6,787 words of 50-word chained sentences — accurate but unreadable).
5. **Explain what every number MEANS**: not '34% owned' but '34% owned — about 1 of every 3 teams will have him'.
6. **Never print a bundle-internal file reference** ('image-35') — describe what the thing is ('the Indy last-four-races chart'). Real source names preferred; spell out an initialism on first use.
7. **Cite everything** (every claim names a specific article line OR a projection number), and state the citation in plain words too. Short tables where they compress.
8. **LENGTH BUDGET (updated 8/11/26 — specificity beats brevity): the slate strategy is at most 2,200 words** — aim 1,500–2,000. The strategy + autopsy review pair may total up to 4,000 words (user directive 8/11/26: "I don't want the strategy and autopsy findings to become too vague"). Per-section spend: Short version ~120 · At a glance ~60 · Edges & tensions ~200 · Field vs Sharp ~200 · Top plays ~400 · Leverage ~250 · Fades ~150 · Build it like a sharp ~300, headroom to whichever section the slate genuinely needs. Trim by SELECTION (drop whole repeated ideas), never by blurring — a finding always keeps its names and numbers.
9. **ONE HOME PER PLAYER.** Each player is EXPLAINED in exactly one section — almost always `## Top plays` (leverage plays in `## Leverage`, fades in `## Fades`). Everywhere else: name + at most five words. Never a second paragraph about the same player — repetition is where the old 6,000-word briefs came from.
10. **NEVER VAGUE (user directive 8/11/26).** Every claim names its subject and its numbers: never "the day's top scorer" without the player's name, never "a cheap golfer spiked" without who/salary/score, never "the screen missed him" without the number it missed by. If cutting words would force a claim to lose its name or number, keep the words. Applies to the slate strategy AND the autopsy review.

Sections, in this order:

1. `## The short version` — **the first thing the user reads and the only section that must stand alone with zero DFS knowledge.** 6–9 numbered single sentences, no sub-bullets, no tables, max one number per sentence: what kind of slate this is; where the points actually come from and why; what the crowd is doing; the ONE decision that most separates entries; what a sharp does differently; the biggest trap. Every term explained in the sentence it appears in. No tiers, no citations — those live below.
2. `## Slate at a glance` — ≤6 lines: games/fights/races, implied totals/win probs, weather, contests + field sizes. A short table. (If the slate looks stale, instead open the doc with a single bold `⚠️` warning line and stop.)
3. `## Edges & tensions` — **THE STAR, up top.** The things that actually matter this slate, SYNTHESIZED — **NOT play/fade calls.** A numbered list, **max 8 lines, each ONE line of ~20 words** (10 lines only if the mandates need the room): **the edge/tension** · the cited data that reveals it. Candidates: where scoring/leverage concentrates, ownership-vs-ceiling mispricings, where vendors/articles DISAGREE (that gap is the edge — absorbs the old `## Key themes`, which no longer exists), substitutable chalk clusters. Mandates, ONE line each: **Anchor-Equivalence MUST appear** (as an observation, never "run the alternative"); every `## Field tendencies` reliably-crowded cluster with its in-N-of-M count (OPPONENT behavior only — never player quality, never "fade X") plus its trap-SHAPE line; the `## Trap-shaped prices` this-slate names; the top `## Chalk combos` pair as a duplication line. NO imperative verbs (PLAY/FADE/run/cap/pair/build) — state the edge and stop; the user decides.
4. `## Field vs Sharp — how this slate gets played` — the head-to-head read, THREE short parts, ~180 words total, players by NAME only (write-ups live in Top plays): **(a) How the FIELD will play it** (~2 sentences) — the anchors/tiers/pairings the typical entry carries, from projected ownership + `## Chalk combos` + `## Field tendencies`. **(b) How a SHARP will play it** (~2 sentences) — from the `## Shark reality` observed envelope applied to THIS slate: anchor tier, where the sub-10% piece lives, what they refuse to share. **(c) The gap** (1–2 sentences) — exactly where the two diverge, concrete enough to build from. (The old part (d) per-player usage essay was DELETED 8/9/26 — it restated Top plays; the sharp's stance is now a one-liner inside Top plays.)
5. `## Top plays` — **the ONE home for every player write-up.** Tiered **Core / Good / Okay** (same vocabulary as the Player pool; Fades live in §7), **at most 12 players**, best as a table, one row each: **player** ($sal, own%) — tier — ONE ~20-word sentence on why, cited — plus a short **sharp stance** for the slate-defining ones ('field ~30%, a sharp runs ~10%'). Append `· Leverage` to any low-owned high-ceiling play.
6. `## Leverage` — **its own section (user directive 7/27/26: leverage and fades are SEPARATE sections, never combined).** The low-owned definers screen, MANDATORY: for EVERY game/fight/race name the single sub-10%-owned high-ceiling play (INCLUDING ones the articles never named). **ONE flat list, ONE line per spot, ~15 words max** — no sub-headers, no price-band subsections, no paragraphs. Every spot gets its line (the non-negotiable fix for the recurring "faded the winning sub-10% definer" miss), and a line is all each spot gets. NO fade verdicts here.
7. `## Fades` — **its own section.** Open with ONE sentence defining the verdicts for the whole section (FADE = play nowhere · LEAN FADE = mostly avoid · UNDERWEIGHT = less than the crowd, never zero). Then one line per player: **NAME — VERDICT** — one ~20-word cited sentence (THIS slate's salary + projection + ownership, and the world the fade needs). (Parsers: `player_pool.parse_calls`/`extract_fades` read the split `## Fades` + `## Leverage` sections AND the legacy combined `## Leverage & fades` + `**Fades:**` sub-header — old archived strategies still parse.)
8. `## Build it like a sharp` — **the closing section, and with `## The short version` the one the user acts on.** The user plays **SINGLE ENTRY almost exclusively** and their stated goal is to MIMIC THE SHARPS (user, 7/26/26). A numbered walk-through of the sharp's decisions, **each step 1–2 SHORT sentences, players by NAME only**: **(1) the anchor decision** — the tier and why, 2–3 candidates with ownership, anchor-equivalence twins flagged; **(2) the leverage piece** — 2–4 named candidates, target anchored to `## Shark reality`; **(3) what a sharp refuses** — the top duplicated pair(s) with counts ('carrying both = sharing the entry with ~N opponents'); **(4) the salary shape** — the anchor's downstream cost in plain arithmetic, and WHICH-chalk-to-drop when it can't all fit; **(5) two contests, two different entries** — only if 2+ declared, each with its own one-sentence reason it wins; **(6) the big-field attack** — ONLY when a 20-Max/150-Max contest is declared (replaces the old separate `## Field attack plan` section, deleted 8/9/26): one ~15-word line per field mistake with slate evidence (mistake · evidence · attack) from the 8-error catalog (self-copying, mispriced own, recency, anchor-twin herding, ignored mid-tier, dead builds, news stampedes, trap-shaped prices), skip silent ones, close with 'the effective field is smaller than listed', still zero lineups; **(7) the pre-lock check** — 3–5 short yes/no questions against the built lineup. Close with the sharp-envelope target in one line, citing a named pro from `## Shark reality` where one exists.

**SUGGESTIONS ARE ALLOWED HERE, in sharp-archetype voice** (user, 7/26/26: "i still dont want you to tell me how to play but suggestions are fine, especially for the sharps/sharks") — e.g. 'a sharp anchors in the $9K tier here', 'a sharp would not carry both halves of that pair'. Still FORBIDDEN everywhere: telling the USER what to do ('you should play X', 'fade Y'), naming a full roster, or presenting any group of players as a build. Describe the sharp's reasoning and name candidates per decision; the user picks.

## Pre-flight ritual (mandatory prep — every slate strategy, but SILENT)

Before writing `data/slate_analysis/<slug>.md`, do ALL of this — but **it is silent prep; NEVER print a `## Pre-flight checklist` section (the user does not want to see it).** Only the RESULT of each step shows, inside the strategy's sections.

1. **Confirm the slate.** Compare the bundle's generation timestamp and the article file dates against today. If the articles look like a prior slate (stale dates), do NOT analyze stale data — instead open the doc with a single bold `⚠️` warning line and stop. The current slate's articles drive everything; past results are reference only.
2. **Read the venue file** (nascar → `rules/nascar/tracks/`, golf → `rules/pga_classic/courses/` for BOTH pga slugs; mma has none). If missing, create a stub from this slate's articles and mark it `**UNVERIFIED — built from this slate's articles only**`.
3. **Read `rules/<slug>/lessons.yaml`.** Apply every lesson with status `hypothesis` or `validated` in the decisions where it fits; silently drop the ones whose mechanism doesn't. Codified lessons live in framework.md already; retired ones are ignored.
4. **Run the framework pre-lock checks** for the sport, always including Anchor-Equivalence (`rules/shared/anchor_equivalence.md`) — surfaced as a tension in `## Edges & tensions`.
5. **Scan `rules/<slug>/results.jsonl`** (last 3 slates) for recent process notes.
6. **Note the universal sharp principles** (`rules/shared/sharp_playbook.md` — reverse-engineered from 12 elite players' DK standings) as the target envelope for the hand-builder: every lineup unique; ≥1 sub-5%-owned leverage piece in most; ~12–16% average ownership per roster slot (sport-calibrated); an elite anchor with downstream differentiation; judged on ceiling, not median.

The strategy opens directly with `## Slate at a glance` (or the `⚠️` stale-slate warning) — never a checklist.

## Lesson ledger (`rules/<slug>/lessons.yaml`)

Structured lessons with a lifecycle: `hypothesis` → `validated` → `codified` (or `retired`). Each lesson: `id`, `born` date, `origin` (history dir), `statement`, `status`, `confirmations[]`, `contradictions[]`, `codified_in`, `retired_reason`.

- Claude updates evidence/status during the post-autopsy review.
- **Codifying into framework.md/philosophy.md and retiring both require user approval** — the review writes proposals; the user clicks "Approve & apply" in the Autopsy tab.
- Promotion criteria: 3 total confirming slates (origin + 2 confirmations of the MECHANISM, not just the result) → propose codifying. 2 mechanism contradictions → propose retiring.
- **GPP guard: a lost contest is never evidence by itself** — only mechanism confirmations/contradictions count. Variance is the game.

### Lesson-ledger hygiene (Autopsy tab)

As ledgers grow past ~20 lessons/sport, the **Lesson-ledger hygiene** block (Autopsy tab, below the post-autopsy review) keeps them sharp. `src/ledger_hygiene.py` computes deterministic flags instantly — **stale** hypotheses (0 confirmations that have had ≥3 logged slates or ≥30 days), **near-promotion** (2 of 3 confirming slates), **overdue promotion** (≥3 confirming slates, not yet codified), and **merge candidates** (`[[id]]` cross-links or high statement-token overlap). The reasoning over those flags rides the **post-autopsy review** (not a separate button): `run_autopsy_review` recomputes them fresh and writes retire / keep / merge / codify decisions into the review's `## Ledger hygiene` section; the same **✅ Approve & apply proposals** button applies them to `lessons.yaml` (+ framework/philosophy for codifications). Same approve-gate + GPP guard: a lesson untested only because no relevant slate occurred is KEEP, not retire; a lesson whose mechanism references a removed feature is a retire candidate.

New ledger file header (when creating lessons.yaml for a sport):

```yaml
# Lesson ledger — one entry per generalizable lesson. Claude edits during the
# post-autopsy review; the user approves codifications/retirements.
# Lifecycle: hypothesis -> validated -> codified | retired.
# Promotion: 3 mechanism confirmations -> propose codifying into framework.md.
# Retirement: 2 mechanism contradictions -> propose retiring.
# GPP guard: a lost contest is NOT a contradiction; only mechanism failures count.
lessons: []
```

## Post-autopsy ritual

Triggered by the Autopsy tab's **Run post-autopsy review** button after **Log autopsy** (which archives the slate to `rules/<slug>/history/<date>__<slate>/` and appends `rules/<slug>/results.jsonl`). The autopsy runs from **DK contest-standings alone** — there are no projections, so there are no proj-vs-actual or vendor-calibration panels. The headless review run:

1. Grades the archived slate's process (checklist honesty, lessons applied vs ignored) and whether the slate strategy's Top plays / PLAY-PASS-MIX decisions held up against the DK actuals (slate-defining low-owned plays, your entries vs the winners, shark gap).
2. Updates `lessons.yaml` evidence/statuses and births new hypotheses (mechanism-based, not result-based).
3. Updates/creates the venue file with a date-stamped per-slate observation.
4. Writes `<history_dir>/autopsy_review.md` — **LENGTH BUDGET (updated 8/11/26 — specificity beats brevity): at most 1,800 words, aim 1,000–1,500; the strategy + review pair may total up to 4,000** — every finding keeps its names and numbers (the Never-vague rule above: "the day's top scorer" is banned — say Benjamin James, $8,700, 84.25 points) — with `## What happened` (~150 w, ≤6 numbered plain sentences: finish, who won and how, the one thing that decided the slate — named), `## Process scorecard` (~400 w — the WHY: two or three specific sentences per finding, each carrying its player names and numbers), `## Lesson ledger changes` (~120 w, one line per lesson), `## Venue file changes` (~40 w), `## Ledger hygiene` (~150 w, one line per retire/merge/promote decision, only when flags exist), `## Proposed codifications` (~150 w) — proposed (NOT applied) framework changes; the user approves via the app — and `## What this means for next slate` (~80 w, 3-5 numbered single-sentence takeaways, most important first). **The review follows the same 5th-grader + keep-it-short writing rules as the slate strategy** (see the Hard writing rules above): exact headers kept (the app parses them), each section opens with one plain sentence saying what it's about, every ledger/DFS term gets the plain-meaning-first treatment ('an idea we are still testing (a hypothesis lesson)', 'whether your entries followed your own plan (adherence)'), analyst vocabulary is translated ('structural axis' → 'the main way winning lineups looked different from yours'; 'Spearman near 0' → 'this pre-lock number did not predict the real scores at all'), every number's meaning is spelled out, every grade comes with a one-sentence what-to-do-about-it, and nothing is said twice.

The slate's scoreboard is **best-percentile trend + process/mechanism metrics** — ROI is tracked in the user's third-party app, so winnings/ROI in `results.jsonl` are optional and usually null. Never flag missing winnings as a gap, never ask the user to backfill them, and never conclude from ROI even when present (high-variance GPP data).

## Hard rules

- **NEVER create lineups.** This tool builds NO lineups — ever. Both generated outputs name **individual plays only**: the slate strategy writes no roster tables / sample builds / "core build" groupings, and the Player pool is a board of single players ranked independently (never combined into a roster, stack, or pairing presented as a build). Applies to in-app generation AND chat sessions. The user hand-builds; construction lives outside this tool. **Grading is not building:** the ✅ Grade tab checks lineups the USER already built and names weaknesses — it must never propose swaps, replacements, or alternative rosters (that would be construction). **Selection is not construction (8/9/26):** the Grade tab's per-contest pick flow (`src/lineup_selection.py` + `run_contest_selection`) may PICK among the Sim's already-built, already-simmed pool lineups — by id, from that contest's candidate slice, validated by `parse_pick` (fabricated/modified/wrong-count/already-picked-elsewhere/strategy-breaking picks are rejected and save nothing). **The pick MUST follow the slate strategy (8/15/26):** the strategy contract is applied as a hard gate on the pool before the slice is cut — sim rank only breaks ties among lineups the strategy already allows, and a slate with no strategy cannot be picked at all. **One lineup, one contest (8/15/26, all sports):** a pool lineup can be picked for only ONE contest on the slate — the pick flow removes it from every other contest's slice, and the portfolio view warns if a repeat is pasted by hand. **Two opinions per contest (8/22/26):** each contest shows the Sim's diversified entries beside claude's own pick, both graded, with an agreement count — the pick is BLIND to the Sim's set (that is what makes agreement evidence), overlap between them is a fine outcome, and a Sim entry that breaks the slate strategy is flagged but never hidden. Showing and grading someone else's lineups is not construction. The user decides in DK. Every roster shown was constructed by the Sim; authoring or modifying a roster stays banned everywhere, and the slate-strategy / player-pool / thesis-grade runners never select.
- **Slate strategy = everything uploaded (articles + every loaded vendor projection); autopsy stays standings-only.** The generated slate strategy synthesizes the uploaded articles AND the loaded projections (folded into the bundle), cross-checked against the strategy docs. The **autopsy** still derives from DK contest-standings alone and never requires projections — but when the slate's projections are still loaded, salary/proj display fields are enriched best-effort (8/11/26; None when cleared/unmatched). The **Projections tab** is also a standalone upload/reference store — but no lineup building/ranking/red-teaming/fixing (that lives in the sim tool; the Grade tab's per-contest picks over the Sim's pushed pool are the one sanctioned exception — see *Selection is not construction*).
- **No scraping.** DK ToS prohibits it; never build scrapers. Use user-pasted/uploaded data only.
- **GPP-only framing.** Leverage / ceiling / contrarian. Never propose cash-game features.
- **Anchor-Equivalence Rule** is a **mandatory surfaced tension** in every slate strategy's `## Edges & tensions`. 4-slate-validated structural leak: if 2+ chalk-tier anchors sit at similar ownership (per the articles), surface that they're substitutable (the user decides whether to run the alternative — the tool synthesizes, it doesn't command).
- **Venue check before any strategy**: read the sport's venue file (NASCAR tracks / PGA courses) per the Pre-flight ritual. For NASCAR specifically, if `rules/nascar/tracks/<slug>.md` is missing, proactively ask the user for the track description.
- **Pre-flight ritual is mandatory** for every slate strategy — chat sessions included, not just headless runs.
- **PGA RD4 SD**: flat 6-golfer lineup, **NO captain, NO 1.5x multiplier**. Never reference "CPT" for this contest type. Position is the live to-par leaderboard score, never the tee time.
- **No NFL/NBA/MLB.** Out of scope. (MLB Classic was removed 2026-07-18 — user dropped the sport; its history lives in git only.)
- **Never commit without explicit instruction.** "done"/"next"/"looks good" are NOT commit triggers.
- **Log autopsy commits LOCALLY; it never pushes (7/25/26).** The learning log (`rules/`) is auto-committed so slate knowledge is never laptop-only, but `git push` takes no refspec — it publishes EVERY unpushed commit on the branch, not just the backup — so publishing is a separate explicit "⬆️ Back up learning log to GitHub" button that first shows exactly what it would send (`git_backup.unpushed_summary`). Logging an autopsy is consent to log an autopsy, not to publish whatever else is on main. Don't make the push automatic again.
